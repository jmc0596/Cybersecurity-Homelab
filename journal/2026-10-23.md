# 2026-10-23 — Kali Dual-NIC Configuration

## Objective

Today I restored internet access for the Kali VM without removing it from the isolated lab network built in Lab 03.

After Lab 03, Kali's only network adapter was connected to `lab-isolated`. That network has no forwarding, so Kali had no internet access for updates or downloading tools.

The objective was to keep the isolated adapter and add a second adapter on the existing libvirt `default` NAT network.

---

## Starting Point

On the Fedora host, I checked Kali's adapters and the available networks:

```bash
virsh -c qemu:///system domiflist Kali-2026
virsh -c qemu:///system net-list --all
```

Kali had one adapter, connected to `lab-isolated`.

Both `default` and `lab-isolated` were active and persistent.

---

## Adding the NAT Adapter

With Kali shut down, I added a second VirtIO adapter on the `default` network:

```bash
virsh -c qemu:///system attach-interface \
  --domain Kali-2026 \
  --type network \
  --source default \
  --model virtio \
  --config
```

The `--config` option saves the change to the VM's persistent definition, so it applies the next time the VM starts.

Kali now has two adapters:

| Network | MAC address | Purpose |
|---|---|---|
| `lab-isolated` | `52:54:00:05:e0:12` | Isolated lab exercises |
| `default` | `52:54:00:d3:cf:a2` | NAT internet access |

---

## Troubleshooting

### Isolated interface had no address

After starting Kali, `eth1` received the NAT address `192.168.122.130/24`, but `eth0` had no IPv4 address.

```bash
nmcli device status
nmcli connection show
```

`eth0` was disconnected and had no saved NetworkManager connection profile.

I created and activated one:

```bash
sudo nmcli connection add \
  type ethernet \
  ifname eth0 \
  con-name lab-isolated \
  ipv4.method auto \
  ipv6.method auto

sudo nmcli connection up lab-isolated
```

`eth0` then received `10.10.10.101/24` through DHCP.

This showed that a virtual NIC being attached and `UP` is not enough on its own. NetworkManager also needs a connection profile before it configures the interface.

---

## Final Configuration

| Interface | IPv4 address | Network |
|---|---|---|
| `eth0` | `10.10.10.101/24` | `lab-isolated` |
| `eth1` | `192.168.122.130/24` | `default` NAT |

Routing table:

```text
default via 192.168.122.1 dev eth1 proto dhcp src 192.168.122.130 metric 100
10.10.10.0/24 dev eth0 proto kernel scope link src 10.10.10.101 metric 101
192.168.122.0/24 dev eth1 proto kernel scope link src 192.168.122.130 metric 100
```

The default route uses the NAT adapter. The isolated subnet is reached directly through `eth0`.

## Reflection

The main lesson was that one VM can use separate virtual adapters for separate purposes, and the routing table decides which one carries each packet.

Testing the isolated gateway, the NAT gateway, an external IP and DNS each checked a different part of the path, rather than relying on a single test.

I also need to be careful about what these tests prove. They show what Kali can reach. They do not prove the isolated network is completely isolated.

Kali is now connected to both networks. Before working with vulnerable targets, I should disconnect the NAT adapter or confirm that IP forwarding is disabled on Kali, so it cannot route traffic between the two networks.
